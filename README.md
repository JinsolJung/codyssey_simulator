# Mini NPU Simulator

입력 패턴과 두 필터의 같은 위치에 있는 값을 곱해 누적하고, 두 MAC(Multiply-Accumulate) 점수를 비교해 패턴을 판정하는 Python 콘솔 프로그램이다. 3×3 콘솔 입력과 5×5·13×13·25×25 JSON 일괄 분석을 지원한다.

## 실행 방법

Python 3.8 이상이 필요하다. 별도로 설치할 패키지는 없다. 코드와 실습 데이터 작성 순서는 [GUIDE.md](GUIDE.md)에 정리했다.

1. `mac_simul` 폴더에 `main.py`를 작성한다.
2. 모드 2를 실행하려면 과제에서 제공한 `data.json`을 `main.py` 옆에 둔다. 과제 파일이 없는 경우 가이드 4-3의 명령으로 실습용 파일을 생성한다.
3. `mac_simul` 폴더의 터미널에서 다음 명령을 실행한다.

```sh
python3 main.py
```

| 선택 | 실행 흐름 |
|---|---|
| `1` 사용자 입력 | 필터 A, 필터 B, 입력 패턴 순서로 입력한다. 각 행렬은 세 줄이며, 한 줄에 숫자 세 개를 공백으로 구분한다. 두 점수, 판정, 3×3 평균 연산 시간을 출력한다. |
| `2` JSON 분석 | `data.json`의 필터와 패턴을 읽고 두 점수, 판정, 기대 라벨, PASS/FAIL을 출력한다. 성능 표와 전체 집계, 실패 케이스 목록을 표시한다. |

모드 1에서 아래 각 칸의 텍스트를 한 줄씩 입력하면 A는 `1.0`, B는 `5.0`이므로 `B`로 판정한다.

| 행 | 필터 A | 필터 B | 입력 패턴 |
|---:|---|---|---|
| 1 | `0 1 0` | `1 0 1` | `1 0 1` |
| 2 | `1 1 1` | `0 1 0` | `0 1 0` |
| 3 | `0 1 0` | `1 0 1` | `1 0 1` |

## 구현 요약

- 2차원 리스트를 이중 반복문으로 순회하며 `pattern[row][col] * kernel[row][col]`을 점수에 누적한다.
- JSON의 `size_{N}_{idx}` 키에서 N을 읽어 `filters.size_N`을 선택한 뒤 두 필터와 입력이 N×N인지 확인한다. 잘못된 콘솔 행은 다시 받고, JSON의 잘못된 케이스는 이유를 기록한 뒤 다음 케이스를 처리한다.
- 필터 키 `cross`와 기대값 `+`는 `Cross`로, 필터 키와 기대값 `x`는 `X`로 변환한다. 표준 라벨로 판정과 기대값을 비교한다.
- 두 점수의 절대 차이가 `1e-9` 미만이면 `UNDECIDED`로 처리한다. 모드 1에서는 이를 `판정 불가`로 표시한다. 모드 2의 기대 라벨은 `Cross` 또는 `X`이므로 동점은 FAIL이다.

## 결과 리포트

아래 결과는 가이드의 코드를 조립해 가이드 4-3의 실습용 데이터로 확인했다. 측정 환경은 macOS(arm64), Python 3.14.6이다.

| 전체 테스트 | 통과 | 실패 |
|---:|---:|---:|
| 8 | 6 | 2 |

| 실패 케이스 | 원인 | 판정 근거 |
|---|---|---|
| `size_13_3` | 부동소수점과 점수 비교 정책 | Cross `0.30000000000000004`, X `0.3`. 차이가 epsilon 미만이라 `UNDECIDED`가 나왔고 기대 라벨 `X`와 달랐다. |
| `size_25_3` | 데이터 크기 불일치 | 키는 25×25를 지정했으나 입력은 1×1이었다. 행 개수 검사에서 FAIL로 처리했다. |

| 크기 | MAC 1회 평균 시간(ms) | 연산 횟수(N²) |
|---:|---:|---:|
| 3×3 | 0.000683 | 9 |
| 5×5 | 0.001387 | 25 |
| 13×13 | 0.007325 | 169 |
| 25×25 | 0.025763 | 625 |

1. 5×5·13×13·25×25마다 십자가와 X의 정상 케이스를 한 개씩 검증해 총 6개가 통과했다.
2. 기대값 `+`와 필터 키 `cross`를 같은 표준 라벨 `Cross`로 맞춰 표기 차이 때문에 실패하는 일을 방지했다.
3. 5×5 십자가 예제에서는 십자가 필터와 검은 칸 9개가 겹쳤고, X 필터와는 가운데 한 칸이 겹쳤다. 콘솔 점수는 각각 9.0과 1.0으로 손계산과 일치했다.
4. `size_13_3`의 점수 차이는 약 `5.55e-17`이었다. `0.1 + 0.2`와 `0.3`의 이진 부동소수점 표현에서 생긴 차이를 epsilon으로 흡수해 근소한 수치 오차로 승자를 고르는 일을 방지했다.
5. `size_25_3`은 MAC을 호출하기 전에 크기 검증에서 실패했다. 이런 경우 케이스 키가 가리키는 크기와 입력 및 필터의 행·열 수를 확인한다.
6. 정상 크기와 표준 라벨을 가진 케이스가 예상과 다르면, 두 점수를 손계산과 비교해 MAC 구현이나 기대 라벨이 틀렸는지 확인한다. 점수가 거의 같으면 허용오차 규칙도 확인한다.
7. 입력과 필터를 먼저 준비하고 `perf_counter_ns()`로 MAC 함수 호출 구간만 크기별 10회 측정했다. 파일 읽기, 배열 준비, 입력, 출력은 평균에 포함하지 않았다.
8. 성능 표는 JSON 모드의 3×3 예제와 5×5·13×13·25×25 합성 행렬을 사용한 결과다. 표의 연산 횟수는 필터 한 개 기준이며 패턴 하나를 두 필터와 비교하면 2N²개의 위치에서 MAC을 수행한다.
9. MAC 한 번은 N개 행에서 각 N개 열을 방문한다. 따라서 총 연산 횟수는 N²이고 한 번의 MAC 호출에 대한 시간 복잡도는 O(N²)이다.
10. 25×25는 5×5보다 MAC 횟수가 25배이며 이번 측정의 평균 시간은 약 18.6배였다. 작은 입력에서는 함수 호출과 타이머의 고정 비용이 상대적으로 크게 반영되므로 시간 비율은 연산 횟수 비율과 다를 수 있다.

과제용 `data.json`을 받으면 모드 2를 다시 실행해 집계, 실패 목록, 성능 표를 실제 결과로 갱신한다. FAIL이 0개라면 모든 케이스가 스키마 검증을 통과했고, 정규화된 기대 라벨이 실제 판정과 일치했으며, epsilon 동점으로 처리된 케이스가 없었는지 확인해 기록한다.
